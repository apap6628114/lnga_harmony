# 主题列表「已读 / 有新回复」标记设计（Topic Read State Design）

本文档定义 `TopicListPanel` 帖子条目（`TopicCardComponent`）上「**没看过 / 看过 / 看过后又有新回复**」
三种状态的数据来源、判定口径与视觉表达。

**生效范围**：所有使用 `TopicCardComponent` 的入口——版面列表、收藏夹（`favor`）、
作者主题/回帖（`author` / `searchpost`）、热门、置顶（均在 `BoardRouter` / `ActivityRouter` 内）。
**不在本期范围**：全局与版块内**全文搜索**走 `SearchPanel` 的 `SearchTopicCard`（另一张卡片），
既无降权也无 `+x`——同一帖在版面列表与搜索结果里的表现因此不同（见 §6.1）。

一句话：**不新增任何图元**——看过的帖子标题与摘要轻轻压暗（浏览器"访问过的链接"那套约定），
"看过后又有新回复"只在底栏回复数后面追加真实增量 **`+x`**（x = 上次进帖时与现在的回复数差）。

---

## 1. 设计目的与硬约束

| 目标 | 落点 |
| --- | --- |
| 区分"看过 / 没看过" | 看过 → 标题与摘要降权（变淡）；没看过 → 保持原亮度 |
| 区分"看过但已更新" | 看过且有新回复 → 底栏回复数后追加 **`+x`**（真实差值，主色）；亮度不变、回复数与气泡颜色不变 |
| **不想太显眼** | **零新增图元**：状态差只由"亮度"与"一段短文本"表达 |

必须同时满足的既有契约（违反任意一条都会引入比"不显眼"严重得多的问题）：

- **条目底色必须透明**（`docs/TITLE_LIST_DESIGN.md` 坑点 1）：列表在 `linearGradientBlur` 渲染层内，
  实色行会在行边缘化出色带 → 因此**不能用整行底色 / 左侧竖条**表达状态。
- **标题颜色与粗斜体是 NGA 服务端下发的**（`titlefont` 位值，见 `getSubjectFontColor` /
  `isSubjectBold`）：**不能**用改标题字色、改字重的方式表达已读——那等于覆盖服务端语义
  （红/金/绿/橙/灰与粗体是楼主自己设置的标题样式）。
- **列表行在 `LazyForEach` 中按 `tid` 复用**：状态变化必须由 `@StorageProp` 版本号驱动重算
  （与 `blacklistVersion` 同一模式，见 `arkui-refresh` skill），且判定必须在
  `build()` 期**同步**完成——不能对每一行发异步查询。

## 2. 视觉语言（三态）

| 状态 | 标题 / 摘要 | 底栏回复数 | 含义（用户视角） |
| --- | --- | --- | --- |
| 没看过 | 原亮度 | `💬 99`（常规色） | 有内容可看 |
| 看过、无新回复 | `opacity(0.7)` | `💬 99`（常规色） | 读过了，没有新东西 |
| 看过、之后有新回复 | `opacity(0.7)`（**不恢复**） | `💬 99`（常规色）+ **`+3`**（主色） | 读过了，多了 3 条新回复 |

两条轴各管一件事：**亮度**只回答"这条我读过没有"；**`+x` 增量**只回答"读过后又多了几条"。
被 v2 回滚的是"让**回复数本身**变色"（同一个数字既表示数量又表示状态）；v3 的 `+x` 是
**新增的信息**，用主色（`AppColors.primary`）承载——与项目既有的「+N 条新回复」同一处理。
回复数与气泡图标**一律保持常规色**（`AppColors.textTertiary`）。`0.7` 定义在
`TopicListPanel.ets` 顶部常量 `TOPIC_READ_CONTENT_OPACITY`，带完整取值理由。

### 2.1 为什么这样选
- **降权只表达"我读过了"**：它不新增任何图元、不改变任何元素的落点，纯靠亮度差。
  扫视时"没看过的帖子更亮"是自然结果，而不是"多了一堆记号"。
- **更新态不恢复原亮度**：亮度轴若同时承载两种语义，"没看过"与"看过但有更新"会挤在同一档，
  扫视时"没看过的优先级"被吃掉——那等于用一个更抢眼的信号换掉了原本最该突出的那一档。
- **更新信号写成"增量文本"而不是"给已有元素染色"**：
  - 颜色是**形容词**（"这条不一般"），增量是**名词**（"多了 3 条"）——后者信息量更大，
    而且不需要用户去猜"变色代表什么"；
  - 它落在**信息所属的位置**上：回复数旁边，语义天然对齐；
  - 它不复用任何既有元素的状态（不像给回复数染色那样会与"这个数字本身的含义"纠缠，
    用户不必怀疑"这个颜色是不是在说回复太多"）；
  - 它仍为零图元：一段 `.fontSize(12)` 的短文本，比任何符号都轻。
  - **为什么 `+x` 自己带主色**：它是全列表唯一"新出现"的信息，且只有 12vp。常规色
    （`textTertiary`）在暖白底上对比度只有约 1.9:1，增量很容易被读成数字的一部分而看不见；
    主色（`#C08A4A`）约 2.9:1，在同样的字号下明显更清晰，又不至于像 v1 的实心圆点那样抢眼。
- **不改标题字重/字色**：见 §1 的服务端语义约束（`titlefont`）。
- **不用整行底色 / 左侧竖条**：见 §1 的渲染层约束；此外色块/竖条的视觉重量远大于一段文本。
- **降权只作用于标题与摘要**：
  - 预览图不降权——给图片降透明度会被读成"还没加载完"；
  - 底栏不降权——它是条目的状态区，**`+x` 正画在上面**；
  - 收藏夹的「取消收藏」按钮不降权——它是操作不是内容，压暗可点入口会被读成不可点。

### 2.2 决策记录（三次调整）
1. **v1：6vp 主色小圆点**（标题首行左侧留白、`opacity(0/1)` 切换、`HitTestMode.None` 防吞点击）
   → 实测观感**过于抢眼**：高饱和实心点在任何一屏里都会先于标题被看到，与"不想太显眼"相反。
2. **v2：回复数改用主色**（更新态同时恢复原亮度）→ 把两种含义压在同一个数字上：
   它既是数量又是状态；且更新态恢复亮度会让"没看过"与"看过但有更新"挤进同一亮度档。
3. **v3（当前）：回复数后追加 `+x` 增量**（主色），回复数与图标一律常规色，更新态保持降权。
   信号从"形容词"变成"名词"（带真实条数），同时消掉了 v2 的亮度档冲突。

v1 顺带暴露的两个副作用（点的纵向位置要折算标题行高、命中测试要防吞点击）也随 v1 一并消失。
三次调整的共同方向是**不断降低更新信号的视觉重量、同时提高它的信息量**；
代价是发现性持续下降（要看到底栏才注意到），这是本设计**刻意选择**的方向。

## 3. 数据来源：浏览历史即已读台账

| 概念 | 数据 | 说明 |
| --- | --- | --- |
| 看过 | `HistoryStore` 的浏览历史中存在该 `tid` | 浏览历史天然等价于"用户打开过的帖子"，无需另建一套存储 |
| 基线 | `BrowseHistoryEntry.replies` | 读到该帖时服务端的回复数（写历史时已经存了，见下） |
| 有更新 | 列表条目当前 `replies` **大于** 基线 | **只认回复数增加，与时钟无关**（设备时间/时区/服务端时间不一致都不影响） |

`BrowseHistoryEntry.replies` 因此是**一份数据两个用途**：① 「浏览历史」页展示当时的回复数；
② 本篇的判定基线。它本来就在 `addFromThreadResult` 中由 `ThreadInfo.replies` 写入，本次
**没有新增任何持久化字段**（旧数据天然可用）。

> ⚠️ 正因为"一个字段两个用途"，**基线必须随条目一起落盘**：基线未知时 `replies` 里存的是
> 哨兵 `-2`，展示层（浏览历史页）对负值按 0 呈现。曾出现过"哨兵只写进内存索引、条目里仍是 0"
> 的实现，那让该帖在**下一次写入或下一次冷启动**（索引按条目重建）后退化成"读到时有 0 条回复"，
> 从而误报 `+全部回复数`（见 §5 第 8 条与 §6.1 的遗留数据边界）。

### 3.1 三态哨兵（`common/utils/TopicReadPolicy.ets`）

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `READ_BASELINE_UNREAD` | `-1` | **从未读过**（不在台账中）→ 不降权、不显示 `+x` |
| `READ_BASELINE_UNKNOWN` | `-2` | **读过，但基线未知**（条目 `replies` 里持久化的就是它）→ 降权、不判定更新（不显示 `+x`） |

"基线未知"来自帖子详情未返回主题信息（`ThreadResult.threadInfo` 为空）的兜底路径：此时拿不到
回复总数。**宁可漏报"有更新"，也不能把刚看过的帖子误标成有更新**——误报会直接误导用户重复点开
同一帖，而漏报只是少一个提示。

### 3.2 状态迁移（用户操作 → 列表表现）

| 操作 | 台账变化 | 列表表现 |
| --- | --- | --- |
| 打开帖子（在线、首页 REPLACE 提交） | 写历史，基线 = `threadInfo.replies` | 该行标题/摘要变淡；`+x` 消失（增量归零） |
| 之后有人回复，用户刷新/翻页 | 条目 `replies` 变大 | 回复数后出现 `+x`（x = 新差值）；亮度不变（仍是"看过"的降权态） |
| 删楼导致回复数减少 | 无 | 不报更新（无 `+x`）；基线在下次打开该帖时自然收敛 |
| 清空浏览历史 / 删除单条历史 | 索引同步清空 / 删除 | 回到"没看过" |
| 阅读历史超出上限（500）被 LRU 淘汰 | 索引同步删除 | 回到"没看过"（刻意接受的语义） |
| 登出 | `reset()` 清空索引 | 全部回到"没看过" |
| 切换账号 | 按 uid 重新载入（`history_key(uid)`） | 按新账号的台账重算 |

## 4. 实现落点

| 文件 | 角色 |
| --- | --- |
| `common/utils/TopicReadPolicy.ets` | **纯判定**：两个哨兵、三态枚举、`resolveTopicReadState`、`isTopicRead` 与 `topicUpdateDelta`（同一个事实的两种视图，可被 Hypium 直接覆盖） |
| `store/HistoryStore.ets` | **已读台账**：`readBaselines` 内存索引（tid → 基线）、同步查询 `getReadReplies`、`preload`；索引与历史列表**同源维护**（载入 / 新增 / 删除 / 清空 / LRU 淘汰） |
| `store/AppStore.ets` | `loadUserData()` 中 `historyStore.preload(uid)`（冷启动与登录后各一次） |
| `pages/TopicListPanel.ets` | **视觉**：`@StorageProp('browseHistoryVersion')`、`readState()` / `readBaseline()` / `currentReplies()` / `contentOpacity()` / `updateDelta()`，标题与摘要的 `opacity`，以及底栏回复数后的 `+x` |
| `test/TopicReadUnit.test.ets` | 判定口径与增量回归（8 个用例，见 §6.2） |
| `test/HistoryReadLedgerUnit.test.ets` | **台账往返回归**（哨兵持久化、LRU 淘汰、删除/清空/重置，见 §6.2） |

### 4.1 刷新链路（关键）

```
打开帖子 → ThreadPanel 提交首页响应 → AppStore.addBrowseHistoryFromThread
        → HistoryStore.insertHistory（写历史 + 推进基线）
        → bumpAppStorageVersion('browseHistoryVersion')
        → TopicCardComponent 的 @StorageProp 变化 → 该行重算 readState → 变淡 / 增量归零
```

台账是**懒加载**的，所以 `AppStore.loadUserData()` 必须**预载**它：否则列表会先按"全部没看过"
渲染一遍，等台账落地后再整屏闪一下（`getBrowseHistory` 首次载入完成时也会 bump 版本号，
以兜住"列表先于台账渲染完成"的时序；`Index` 页在 `appStore.init` 完成后才路由到主页面，
正常情况下不会走到这条兜底）。

## 5. 坑点清单（改动前逐条对照）

1. **判定必须在 `build()` 期同步完成**：`build()` 不能 `await`，逐行发异步查询也不可接受 →
   台账必须是内存索引（`Map`），查询 O(1)。**不要**把状态塞进 `LazyForEach` 的 key 或
   data source（那会引发整表重建，见 `docs/TOPIC_PREVIEW_DESIGN.md` §9.2）。
2. **首次载入也要 bump 版本号**：只在写入路径 bump 的话，"台账在列表渲染之后才载入"的那一帧
   会永久停在"没看过"（行不会自己重算）。
3. **索引与历史列表必须同源**：新增/删除/清空/LRU 淘汰四条路径都要动索引；`insertHistory` 里
   把基线写进条目再重建索引（不再另行覆盖内存索引）。
4. **降权只加在标题与摘要这两块"内容"上**（标题行的类型标签与标题、摘要及其屏蔽占位，共四处
   文字节点），不要加在 `Column`（会把预览图、底栏、取消收藏按钮一起压暗，而**底栏正是 `+x`
   所在**——压暗它，更新信号就一起变哑了）。
5. **不要给回复数/图标改颜色**：更新信号只由 `+x` 这段文本承载（它是全列表唯一带主色的元素）。
   给回复数本身染色会与"这个数字的含义"纠缠（用户会怀疑"这个颜色是不是在说回复太多"），
   也让"亮度 + 颜色"两条轴互相干扰（§2.2 决策记录里 v2 被回滚的原因）。
6. **`+x` 不做上限截断**：差值就是列表回复数与基线的真实差额，"回复数涨了 300 却只显示 +99"
   是自相矛盾。要收窄宽度只能改字号/间距，不能改语义。
7. **`+x` 用 `Text` 而不是新图元**（圆点、角标、竖条、底色）：本设计的全部状态差 = 一个
   `opacity` + 一段短文本，新增任何符号都会把"不显眼"这条前提推翻。
8. **基线哨兵必须随条目落盘**（`insertHistory` 里的 `entry.replies = baseline`）：索引在每次写入
   与每次冷启动都会按条目 `replies` 重建，哨兵只放内存索引的话会被重建成 0（"读到时有 0 条回复"），
   该帖随即误报 `+全部回复数`。这是本设计**唯一**"数据层不变量"级别的坑，回归见 §6.2 的台账用例。
9. **重建索引必须防御形状**：`rebuildReadBaselines` 跑在 `AppStore.init` 关键路径上，而该路径的
   异常会让 `AppStore.init` 抛出、`Index` 页停在"应用初始化失败"。取值一律经 `String(...)` /
   `normalizeBaseline(...)`，不直接访问可能被写坏的 JSON 字段。

## 6. 边界与验证

### 6.1 已知边界（刻意不做）

| 项 | 现状 | 原因 |
| --- | --- | --- |
| 台账容量 | 500（沿用浏览历史上限） | 超出后最早读过的帖子回到"没看过"；为一个视觉标记再存一份台账不划算 |
| 离线存档入口 | 不写浏览历史 → 读了也不会变淡 | `ThreadPanel` 刻意不记录存档帖（历史条目以在线通道打开会形成死链） |
| 全文搜索入口 | `SearchPanel.SearchTopicCard` 不参与（无降权、无 `+x`） | 那是另一张卡片（自绘底栏）；要覆盖需把 `readState()` / `updateDelta()` 接进去，本期不做 |
| 遗留的"未知基线"条目 | 旧数据里的 `replies = 0` 无法回溯区分"真 0 回复"与"当时拿不到总数" | 哨兵是本次才引入的；这类条目在首次重新打开该帖后自然收敛 |
| 只看回复数 | 回复数不变（仅编辑内容）→ 无 `+x` | 与跟踪系统同口径（"检查只认总回复数增加"），且列表不提供编辑时间 |
| 自己回复自己 | 回复成功后到再次打开该帖之前，该帖会带 `+x`（含自己那条） | 基线只在**打开帖子**（首页 REPLACE）时推进，而回复成功走的是静默合并不经该路径；跟踪系统同样把"自己回复"计为 +1 条新回复，口径一致。要消除它只需在 `ThreadPanel.silentRefreshAfterPost` 里复用同一次响应再记一次浏览历史（本次不做） |
| 增量按"回复数"而非"楼层数" | 回复数与列表口径完全一致 | 与列表展示的回复数同源，不会出现"显示 99 却说 +100" |
| 跨设备 | 已读状态不跟随账号 | NGA 没有服务端已读接口，本地台账无法同步 |

### 6.2 验证

- **Hypium Local Test，判定层**：`entry/src/test/TopicReadUnit.test.ets`（套件 `topicReadState`）
  覆盖未读基线、回复数不变 / 增加 / 减少、0 回复帖的首个回复、基线未知不误报、当前回复数缺失
  或非法按 0 处理，以及增量不截断（`+320`）。
- **Hypium Local Test，台账层**：`entry/src/test/HistoryReadLedgerUnit.test.ets` 用真实
  `PreferencesStore` + `SerialQueue` 驱动 `HistoryStore`，覆盖：未知基线**经一次写入与一次
  冷启动重载后仍是未知**（§5 第 8 条的回归）、写入会推进基线、LRU 淘汰后回到未读、
  删除/清空/登出重置后索引为空。
- **编译门禁**：DevEco / hvigor 构建（见 `harmonyos-build-deploy` skill）。
- **不在 Local Test 覆盖范围**：`+x` 的观感与可辨识度、`@StorageProp` 驱动的行重渲染
  时序——这些只能在真机/模拟器上人眼核对。

### 6.3 真机核对清单

1. 打开一个帖子后返回列表：该行标题与摘要变淡，底栏回复数后没有 `+x`（同屏未读过的行保持原亮度）。
2. 等该帖有新回复后刷新列表：该行**亮度不变**，回复数后出现 `+x`，且 x 与"当前回复数 − 上次进帖时回复数"一致。
3. 再点进该帖并返回：`+x` 消失（基线已推进）。
4. 深浅色主题各看一遍：① 降权后的标题/摘要仍可读（亮色下标题由 `#3E2A1D` 落到约 `#78685E`，
   对比度约 5.1:1）；② `+x` 的主色与常规色回复数能分开，且不刺眼；
   ③ `+x` 与回复数、作者名、时间在同一行时不挤在一起（间距 4vp），
   数字较大时（如 `+320`）也不与左侧作者信息重叠或把版面名挤没。
5. 顶部标题区滚动压暗/模糊时，`+x` 与其余底栏文字以同样方式被模糊（说明它在 List 渲染层内，
   未被特殊处理）。
6. 「浏览历史」页清空后返回列表：全部行恢复原亮度，且不再有 `+x`；浏览历史页自身对
   "基线未知"的条目显示 0（不出现负数）。
7. 收藏夹（`isFavorites`）与作者主题/回帖列表各扫一眼：状态表现与版面列表一致
   （全文搜索页不适用，见 §6.1）。
