## 2. 树结构：只有两层，所有回复平铺

### 2.1 数据模型（接口口径）

B 站评论数据结构中每条评论都有 `root` / `parent` 两个关系字段（XHR 实测字段名 `root` / `parent` / `dialog`）：

- `root` = 所属**根评论**的 rpid；根评论自身 `root = 0`。
- `parent` = **直接回复对象**的 rpid（可能是根评论，也可能是另一条子回复）。
- `dialog` = 该「对话」首条回复的 rpid（用于对话内定位）。

官方技术博客（《B站评论系统架构设计》，cv20346888）中的建表与查询逻辑印证了这一点：子评论表按 `root` 索引，`SELECT id FROM reply_index WHERE obj_id=? AND obj_type=? AND root=? ORDER BY like_count LIMIT 0,3`；并明确写道：

> 「产品形态上，单个页面只有二级列表（更多嵌套层次，对应嵌套多次点击），且评论计数也只有两级。」

### 2.2 实际渲染规则（一手实测）

- 根评论（一级）单独成卡片，左侧大号头像。
- 其下**所有**回复（不管用户是回复根评论、还是回复另一条子回复、还是回复更深层）**全部平铺在同一级**，缩进相同，不做树形缩进。
- 「回复了谁」这件事不通过缩进表达，而通过每一行正文前的 `回复 @某人 :` 前缀表达（见第 3 节）。
- 因此视觉上永远是「一层根 + 一层平铺子列表」，即用户所说的「树只有两层」。

### 2.3 ASCII 结构示意（B 站网页端实际形态）

```
┌─ bili-comment-thread-renderer（一条根评论 = 一个 thread）
│
│  (48px)  用户名 LV6          ← 根评论：头像 48×48，正文 16px/26px
│          根评论正文……
│          2026-11-03 14:36   👍4392   [回复]   [更多 …]
│
│     (24px) 用户名 LV5  ← 子回复 1：头像 24×24，整体缩进到根评论文本列
│            子回复正文……
│            2026-11-03 14:36  👍994  [回复]
│
│     (24px) 用户名 LV4
│            回复 @某某 : 这是一条「回复子回复」的内容   ← 深层回复平铺，仅加 @ 前缀
│            2026-11-03 12:51  👍369  [回复]
│
```

## 3. 子回复折叠：默认条数、阈值、文案、展开行为

### 3.1 默认显示条数 = 2（一手，XHR 证据）

`GET https://api.bilibili.com/x/v2/reply/main?type=1&oid=...&next=0&mode=3`（热门排序）的响应里，每条根评论自带 `replies` 数组作为「预载子回复」。实测 8 条根评论的预载长度为 **2**（置顶评论 `top_replies` 为 1）：

```
axgsgjh     rcount=108  replies=2   sub_reply_entry_text=共108条回复
石榴守护者   rcount=24   replies=2   sub_reply_entry_text=共24条回复
范范很up     rcount=119  replies=2   sub_reply_entry_text=共119条回复
...（全部为 2）
```

前端渲染逻辑（JS 源码实测）：

```js
// bili-comment-replies-renderer
e.pageSize = 10,
e.showViewMore = true,
this.list = this.data.replies || [],          // 初始只渲染接口预载的 replies（2 条）
this.count = this.data.rcount,                // 子回复总数
this.totalPage = Math.ceil(this.count / this.pageSize)
```

即：**默认渲染条数 = 接口预载条数（2）**，而不是前端写死 3/5。渲染后若 `count > list.length`，底部出现折叠行。

### 3.2 折叠入口文案（一手，DOM 原文）

```html
<div id="view-more">
  <span>共133条回复，</span>
  <bili-text-button>点击查看</bili-text-button>
</div>
```

- 原样文本：`共133条回复，点击查看`（**中文全角逗号**，逗号后无空格）
- 变体：`共59条回复，点击查看`、`共8条回复，点击查看`、`共6条回复，点击查看`
- 前端 JS 文案常量（官方生产 JS 中直接提取）：
  - `totalReplies: "共{$0}条回复"`
  - `clickToView: "点击查看"`
- 样式（computedStyle）：
  - `font-size: 13px`，`color: rgb(148,153,160)`（= `#9499A0` 灰），普通字重
  - 位于楼中楼列表末尾，左边与根评论文本列对齐（继承 `#expander` 的 `padding-left: 80px`）
  - `height: 21.5px`，与上方子回复间距约 4~8px

### 3.3 点击「点击查看」后的行为（一手，交互实测）

实测（登录态，根评论 59 条回复）：

1. 点击后**就地展开**，先加载并渲染**第 1 页 10 条**子回复；
2. 底部折叠行被替换为**分页器**：

```html
<div id="pagination">
  <div id="pagination-head">共6页</div>
  <div id="pagination-body">
    <bili-text-button data-idx="0">1</bili-text-button>
    <bili-text-button data-idx="1">2</bili-text-button>
    ... （超出 5 页时显示 1..5 ... N，末页直达）
    <bili-text-button>下一页</bili-text-button>
  </div>
  <div id="pagination-foot"><bili-text-button>收起</bili-text-button></div>
</div>
```

3. 分页控制走接口 `x/v2/reply/reply?oid=&type=&root=&ps=10&pn=N`（`ps = pageSize = 10`），**每次只加载 10 条，不是一次展开全部**；
4. 点击「收起」→ 回到折叠态，重新只显示 2 条 + `共N条回复，点击查看`；
5. 展开/收起不改变 URL、不跳页。

> 注意：网上常见的「点击后一次展开全部」说法**不准确**——B 站网页端是「展开第一页 + 分页器」。抓全量需要点击或脚本辅助（这正是各类油猴脚本存在的理由）。

### 3.4 未登录行为（一手 JS 逻辑 + 二手说明）

```js
this.user
  ? (this.cacheList = x(this.list),
     this.count > this.pageSize ? this.showPagination = true : this.showViewMore = false,
     this.getList())                       // 登录：加载第 1 页
  : Bw({ event: "selfDef.replyCardCheckClick" })   // 未登录：只埋点，不加载（引导登录）
```

- 未登录时点击 `点击查看` **不会加载**楼中楼，只做登录引导；相关文案常量有 `loginToSeeMore: "登录后查看更多评论"`。
- 二手旁证（Greasy Fork 脚本说明）：未登录 B 站网页端「官方预设仅允许载入两条回复」，并存在「登录后查看更多评论」的限制。
- 本报告实测均在**登录态**完成。

### 3.5 移动端 App 行为（推测 + 接口一手字段）

App 端 UI 无法直接实测，但服务端为每条根评论下发了 App 专用的入口文案：

| 字段 | 实测值 | 含义 |
| --- | --- | --- |
| `reply_control.sub_reply_entry_text` | `共108条回复` | App 楼中楼入口文案（推测用于「共N条回复 ＞」入口行） |
| `reply_control.sub_reply_title_text` | `相关回复共108条` | App 进入「回复列表/评论详情页」后的标题 |

推测的 App 交互闭环（依据：入口文案字段 + `pageSize/排序` 接口参数 + 常见交互形态 + 用户口述「超过 3 个只显示 2 个，点击查看更多」）：

1. 楼中楼默认展示 2 条子回复；
2. 底部出现「共 N 条回复」入口（灰字 + 右箭头）；
3. 点击进入**独立回复列表页**（标题「相关回复共 N 条」），支持「按热度 / 按时间」排序，上拉分页加载；
4. 在列表页内再点某条回复的「回复」→ 打开输入框并 @ 对方；
5. App 端无法跨页定位到具体楼层，分享定位能力弱于网页端（见 3.6）。

> 建议实现时优先采用**网页端**的「就地展开」方案（与 NGA 阅读流更契合），App 的「独立列表页」作为备选。

### 3.6 评论定点定位（一手，官方说明文章）

B 站网页端支持通过 URL hash 定位到具体评论：

```
https://www.bilibili.com/video/av{aid}/#reply{rpid}
```

- 「回复我的 / 收到的赞」消息点击后即通过该机制导航到对应评论；
- **App 端该链接只定位到稿件、不能定位到评论**（官方文章原话：「导航链接只在PC端生效，APP上只会前往对应稿件」）；
- 对楼中楼回复，必须用**回复本身的 rpid**（而不是主楼 rpid）才能定位到那条回复。

## 4. 「回复 @某人」的表达与点击行为

### 4.1 渲染形态（一手，DOM 原文）

子回复内容在 `bili-rich-text` 的 Shadow DOM 内被渲染成（真实样本，被回复者「月夜凉光」）：

```html
<p id="contents">
  <span>回复 </span>
  <a href="//space.bilibili.com/152867413" target="_blank"
     data-type="mention" data-user-profile-id="152867413">@月夜凉光</a>
  <span> :你肯定没懂他是什么意思，ds 模型训练不够……</span>
</p>
```

对应用户看到的原样文本：

```
回复 @月夜凉光 :你肯定没懂他是什么意思，ds 模型训练不够，指令打错导致的意外删除，根本不是正常删的
```

要点：

- `回复 ` 是普通文字（**不是按钮、不可点击**）；
- `@月夜凉光` 是**蓝色链接**（`--bili-rich-text-link-color: #008AC5`，hover 变 `#00AEEC`），`target="_blank"` 指向用户空间；
- 冒号是**半角 `:`**，冒号后**无空格**直接接正文；
- 该前缀实际是**内容的一部分**：XHR 里 `content.message` 字段本身就存了 `回复 @月夜凉光 :正文…`，并同时在 `content.members` 里给出被 @ 用户信息（前端把 `@名字` 片段解析成 mention 链接）；
- 位置：**正文行首**（不是用户名右侧）；同样出现在**普通回复**里，只有「回复了某条子回复/根评论」的回复才带此前缀，直接回复根评论的第一层子回复不带。

### 4.2 点击「@名字」（一手）

- 网页端：`<a href="//space.bilibili.com/{mid}" target="_blank">` → **新标签页打开用户空间**。
- 无「用户信息小卡片 / 气泡」。
- 移动端 App（推测+用户观察）：点击 @名字 / 用户名进入用户个人主页（全屏），B 站没有 NGA 那种资料卡气泡。

### 4.3 其他点击行为（一手实测）

| 交互 | 网页端实际行为 |
| --- | --- |
| 点击子回复「回复」按钮 | 打开评论输入框；输入框 placeholder 变为 `回复 @{用户名} : `（JS 常量 `replyTo: "回复 @{$0} : "`）。楼中楼内嵌回复框由 `bili-comment-box` 组件复用渲染 |
| 点击子回复卡片主体（正文/空白） | **无跳转**（只做埋点 `handleClickTrack(1)`） |
| 点击根评论/子回复的用户名、头像 | 新标签页打开用户空间 |
| 点击时间戳 | 无跳转（仅特定脚本/场景有行为） |
| 查看「对话」 | 网页端**无原生入口**；第三方脚本才有「查看对话」。JS 里仅有 `viewDialog: "查看对话"`、`commentDetail: "评论详情"`、`dialogDetail: "对话详情"` 等常量（用于其他业务位） |
| 楼中楼排序 | 网页端楼中楼分页按接口返回顺序；根评论可「按热度 / 按时间」切换 |

## 8. 对 NGA 场景的适配建议

### 8.1 NGA 与 B 站的差异清单

| 维度 | B 站 | NGA（本工程） |
| --- | --- | --- |
| 楼层身份 | 根评论 rpid / 子回复 rpid，**无楼层号** | 有 `pid` + **楼层号 `lou`**（本工程 `PostInfo.lou` / `PostInfo.pid`） |
| 回复关系 | 无引用正文，靠 `parent` + 内容里的「回复 @」表达 | **有 quote 引用块**（被引用楼层 pid/tid/楼层号） |
| 身份标记 | UP 主标记、置顶 | **楼主标记**、匿名楼层（`authorKey` 稳定标识）、黑名单/备注 |
| 树深度 | 2 层（产品定义） | 论坛语义是**扁平楼层流**，quote 关系天然构成「楼层 → 回复楼层」的两层关系 |
| 评论计数 | 根评论有子回复数 `rcount` | 无「子回复数」字段，需**本地按 quote 关系聚合** |
| 定位能力 | 网页端 `#reply{rpid}`；App 弱 | 已有 `scrollToPid` + `#/thread?tid=&pid=` 页内定位能力（`ThreadPanel.handleLinkClick`） |
| 用户信息 | 新标签打开空间（web） | 已有**资料卡气泡** `showProfileCard(uid, x, y)` |

### 8.2 NGA 的「两层树」映射方案

用户需求原话：「类似 Bilibili 手机端或网页端的有限层树（两层）……树只有两层，当内部全部子叶数量超过 3 个，只显示 2 个，点击查看更多」；「内部 ListCell 增加 X1 回复 X2 的表达，放当前用户信息区用户名右侧，加『回复@XXX』『->』；可点击名字打开用户信息小UI，可点击『->』前往回复内容的 ListCell」。

建议的映射：

1. **根节点 = 被回复的楼层**（一般是被 quote 的楼；若引用链指向更早楼层，取「当前窗口内被引用次数最多/最早」的楼层作为根，避免多级嵌套）。
2. **子节点 = 引用了该根节点的楼层**（按 `.lou` 升序，即时间顺序，与 NGA 论坛阅读习惯一致）。
3. 引用链深度 > 2 时（A 引用 B、B 引用 C、C 引用 D…），D 的引用回复**平铺到根节点下**（对齐 B 站「所有回复平铺到根评论下」的产品规则），不增加缩进；用头部 `X1 回复 @X2` 表达直接回复对象。
4. 只显示「根 + 一级子」两层；更深的层级不展开为新的一层，而是依赖 `->` 跳到被回复楼层后再以该楼层为根继续阅读（对齐 B 站「更多嵌套层次对应嵌套多次点击」）。

> 备选方案：若实现上更希望保持 NGA 的楼层流不变，也可以做「每个楼层卡片内的子回复区块」（等价于把 B 站的 thread 结构放进每个楼层）：楼层 = 根评论，引用它的楼层 = 子回复平铺。两者数据结构一致，只是宿主容器不同。

### 8.3 折叠参数建议（可直接采用）

| 参数 | 建议值 | 依据 |
| --- | --- | --- |
| 子回复默认显示条数 | **2** | B 站接口预载 2 条（一手） |
| 折叠阈值 | **子回复总数 > 3 时折叠**（1~3 条全部内联显示；>3 条时显示前 2 条 + 折叠行） | 用户口述「超过 3 个只显示 2 个」；B 站等价于 >2 折叠，NGA 取 3 更保守、更贴合用户预期 |
| 折叠行文案（主选） | `共 {N} 条回复，点击查看` | B 站网页端原样（一手） |
| 折叠行文案（备选，对齐 App） | `共 {N} 条回复` + 右箭头 `›` | B 站 App 服务端字段 `sub_reply_entry_text`（一手） |
| 展开行为（主选，推荐） | **就地展开**：一次展开全部子回复（NGA 单楼层引用数通常 < 10，无需分页）；超过 20 条时再退化为「展开 10 条 + 再加载」 | B 站网页端「就地展开第 1 页 + 分页」简化版 |
| 展开后收回入口 | 列表末尾放 `收起`，点击回折叠态 | B 站 `收起`（一手） |
| 展开状态持久化 | 建议**不持久化**（离开页面即复位），可按楼层 pid 记在内存 map；避免 `LazyForEach` 复用错位 | 工程实现建议 |
| 加载策略 | 引用关系随楼层数据本地聚合，折叠不触发网络请求；展开只做本地渲染（除非引用楼层不在当前窗口，则走 `scrollToPid` / 加载对应页） | NGA 已有窗口化加载 |

### 8.4 子节点头部布局建议（「X1 回复 X2」+「->」）

用户要求：把 `X1回复X2` 放在**当前用户信息区用户名右侧**，并加「回复@XXX」「->」。

对齐 B 站 + NGA 现有信息区，建议头部结构：

```
┌ 子节点头部（单行，14vp 高）
│
│  [小头像 24vp/20vp]  X1作者名  [楼主标记]   回复 @X2作者名  [->]
│                       ↑ 现有 PostItem 作者信息区      ↑ 蓝色可点      ↑ 可点跳转
│
│  正文（引用块可折叠为 1~2 行摘要，点击展开全文）
│
│  楼层号 · 时间 · 操作按钮（回复 / 举报 / 更多）
└
```

具体建议：

1. **「X1 回复 X2」的表达**：
   - `X1` 用作者名（已有）；`X2` 用被回复楼层作者名（从 quote 解析出的 `pid`/`lou` 反查当前窗口内的 `PostInfo.author`）；
   - 文案建议：`回复 @{X2}` 蓝色（对齐 B 站 `@名字` 的蓝色链接），前面可加一个浅灰 `回复` 二字（对齐 B 站 `回复 @xxx` 的「回复」为普通文字）；
   - 位置：作者名右侧，**不进入正文行首**（这是与 B 站不同的刻意偏离——NGA 的引用关系是结构化数据，放头部更清晰，也更符合用户明确要求）。
2. **`->` 跳转按钮**：
   - 建议用 `→`（U+2192）或图标，`text`/图标按钮，点击热区 ≥ 32vp；
   - 点击行为：定位到被回复的楼层 ListCell（`scrollToPid(targetPid)`，已有能力）；
   - 若目标楼层不在当前加载窗口：走现有引用跳转逻辑（`#/thread?tid=&pid=` + 服务端单帖视图兜底，`handleLinkClick` 已实现）；
   - 定位后建议**短暂高亮**（如背景色 600ms 渐隐），对齐 B 站 `#reply{rpid}` 定位的观感。
3. **「点击名字打开用户信息小 UI」**：
   - 复用现有 `onProfileClick(uid, screenX, screenY)` → `showProfileCard(...)` 资料卡气泡（NGA 已有，优于 B 站的新标签跳转）；
   - `X1`、`@X2` 两处名字都应可点：`X1` 打开 `PostInfo.authorKey/authorid` 的资料卡，`@X2` 打开被回复楼层作者的资料卡。
4. **楼主标记/匿名**：沿用现有 `PostInfo.authorKey` 判定（不要用 `authorid`，匿名楼层 id 不稳定），放在 X1 名字后。

### 8.5 视觉参数建议（ArkUI，单位 vp）

> 换算原则：B 站网页端 16px 正文 ≈ NGA 移动端 16vp；缩进按移动端手屏比例收敛（网页 80px 缩进过宽，移动端取 36~44vp）。

| 元素 | 建议值 | 说明 |
| --- | --- | --- |
| 子节点整体左缩进 | **36~40vp**（相对根楼层卡片内边距） | 比 B 站网页 80px 收敛；保证小屏仍有正文宽度 |
| 子节点头像 | **24vp** 圆形（或 20vp，视现有 PostItem 头像规范） | 对齐 B 站 24px |
| 子节点内头像右边距 | **8~10vp** | 对齐 B 站 34px = 24+10 |
| 子节点上下内边距 | **8vp** | 对齐 B 站 `padding: 8px 0` |
| 子节点正文字号 | 与根楼层一致（不缩小）；如需区分可 -1vp | B 站子回复与根评论正文同为 16px |
| 子节点作者名 | 13~14vp / Medium | B 站 14px / 500 |
| 折叠行字号/颜色 | **13vp / 灰色**（如 `#9499A0`；暗色主题用对应灰） | B 站 13px `#9499A0` |
| 折叠行点击热区 | 整行可点，高 ≥ 36vp | 移动端可点性 |
| 竖线/背景块 | **建议不加竖线**；如要表达层级，用 1vp 浅色左边线（`#F1F2F3` 级别）+ 缩进 | B 站楼中楼**无背景块、无竖线**，纯缩进 |
| 子节点之间分隔 | 无分隔线，靠 8vp 上下间距 | 对齐 B 站 |
| 折叠行与上方子回复间距 | 4~8vp | 对齐 B 站 |
| 高亮反馈（`->` 定位后） | 背景淡色 600ms 渐隐 | 工程自定义 |

| 交互 | 建议行为 |
| --- | --- |
| 根楼层卡片 | 保持现有；若其存在子回复，在卡片底部展示「子回复区」（2 条 + 折叠行） |

### 8.7 实现注意（结合本工程既有约束）

1. **展开/收起要驱动刷新**：`LazyForEach` 键值不含内容变化，展开状态必须进键值或走 `uiRev`（参考 `docs/` 中 `arkui-refresh` 的既有结论：`PostInfo.uiRev` 就是为此设计的）。建议给树节点数据源加 `expandRev`，展开/收起时自增。
2. **不要在网络层请求「子回复数」**：NGA 没有 `rcount` 字段，子回复数由本地 quote 关系聚合（`Map<rootPid, PostInfo[]>`），聚合结果随窗口加载增量维护。
3. **引用解析**：复用现有 quote 解析得到的 `pid`（`#/thread?tid=&pid=` 链路已存在）；找不到目标楼层时按现有逻辑「页内找不到 → 服务端单帖兜底」（见 `ThreadPanel.handleLinkClick` 注释）。
4. **匿名楼层**：子节点作者身份判定一律用 `PostInfo.authorKey`（`authorid` 仅用于资料卡/黑名单 uid 语义）。
5. **离线存档**：目标楼层不在存档窗口时，`->` 应给出与现有引用跳转一致的提示（现有代码：`isSavedSource()` → toast「该楼层未包含在存档中」）。
6. **视觉资源**：折叠行颜色、字号、缩进建议落 `resources/base|dark/element/*.json`，不要硬编码字面值（工程规范）。
