# 跟踪帖子更新 — 设计说明

面向「关注的帖子有新回复时提醒我去看」这一需求：用户在帖子页开启跟踪后，应用在前台
定时查询该帖的服务端回复数，有新回复时在消息中心「跟踪」Tab 亮红点，点开即已读。

## 1. 口径（产品语义）

| 项 | 取值 | 说明 |
|---|---|---|
| 什么算「更新」 | **服务端总回复数增加** | 只认 `__T.replies` 增长；楼主编辑主楼、改标题不算更新（检查时静默回填标题） |
| 删除楼层 | 不算更新 | 回复数减少时只同步基准，未读数按 0 处理 |
| 跟踪时长 | 无新回复满 N 天即停止 | 每次检查都用**最后活动时间**重算；来新回复自动重新计时 |
| 「最后活动时间」 | `max(服务端最后回复时间, 开始跟踪时刻)` | 取较晚者：对一个已停更三天的帖子点「开始跟踪」，若只认服务端时间，任务会在几秒内被判超期删掉；以添加时刻兜底后每个新任务至少有完整 keepDays 观察期，之后有新回复则计时切回真实活跃时间 |
| 时长档位 | 1 / 2 / 3 / 7 / 15 / 30 天 | 默认 2 天（`TRACK_KEEP_DAYS_OPTIONS` / `TRACK_DEFAULT_KEEP_DAYS`） |
| 帖子失效 | 立即停止跟踪 | 被删除 / 锁定 / 待审核 / 权限不足；服务端报告原因一并提示 |
| **失效判据** | 只认 `data.__MESSAGE` | `NgaClient` 会把**任何** HTML 页面（频率限制页 / 维护页 / WAF 页 / 登录跳转页）归一化成 `{error:{0:…}}`；若拿它当失效依据，一次服务端抖动就会清空用户的全部跟踪任务。因此 `ThreadStatusParser` 的「无 data」与「无 `__T`」两条分支都只在存在 `data.__MESSAGE`（NGA 业务错误体）时才判失效，顶层 `error` 仅作失败诊断文案 |
| 跟踪数量上限 | 50 | 超出拒绝新增并提示（`TRACK_MAX_COUNT`） |
| 账号归属 | 按账号隔离 | 用缓存信封 `tracked_threads_<uid>` 持久化（检查必须用该账号 token） |
| 红点 | 应用内 | 并入标题栏铃铛角标；不做系统通知、不做后台检查 |

## 2. 检查通道（实测依据）

`read.php` App 签名 POST + `__output=8`，响应按 **GB18030** 解码
（`NgaClient.postSignedPathGb`）。选它而非帖子详情的 `__output=17` HTML 通道：

| 通道 | 响应体 | 需要 HTML 解析 | 失效可判定 |
|---|---|---|---|
| `__output=8`（本功能） | 实测 20 077 B（page=1） | 不需要，直接读 `__T` | `error` + `data.__MESSAGE` |
| `__output=17`（帖子详情） | 实测 64 397 B | 需要（taskpool 整页解析） | `template=std_error` |

实测要点（`ngabbs.com`，登录态，2026-09）：

- 正常响应：`data.__T` 是**直接对象**（`{fid,tid,subject,locked,replies,lastpost,…}`），
  `data.__ROWS` = 总行数（含主楼），与 `replies` 恒差 1；`replies` 缺失时以 `__ROWS-1` 兜底。
- 失效响应（如 `tid=999999999`，137 B）：
  `{"error":{"0":"2048:找不到主题",…},"data":{"__MESSAGE":{"0":2048,"1":"找不到主题","3":200}}}`。
- **编码**：该通道响应体恒为 GBK（响应自带 `"encode":"GBK"`），实测 `__inchst=UTF8`、
  `Content-Type: charset=GBK`、空 `__inchst` 三种写法都改不动。签名通道默认按 UTF-8
  解码会把中文标题解成替换字符，因此新增了按 GB18030 解码的入口。
- 停更/超期判定用 `lastpost`（服务端最后回复时间），不用「上次检查时间」：
  断网或长期未打开应用不会让活跃帖子被误判停更。

## 3. 调度与成本

- **前台 10 分钟轮询**（`TRACK_POLL_INTERVAL`，接入 `AppStore.pollingParticipants`，
  与通知/动态轮询同一套「初始化 + 前台 + 已登录」门禁）。
- 一轮内**逐帖串行**检查，帖间留 400 ms（`TRACK_CHECK_GAP`），避免请求突发触发风控。
- 单帖另有 60 s 最小检查间隔（`TRACK_MIN_CHECK_INTERVAL`）：点开帖子触发的即时检查按此节流。
- 全量检查有 `refreshing` 并发闸门；非强制刷新受 30 s 最小成功间隔约束
  （`BaseStore.runGuardedRefresh`）。
- 流量上界：50 帖 × 20 KB × 6 轮/小时 ≈ 6 MB/小时（仅前台、仅已跟踪的帖子）。

## 4. 停止跟踪的三个出口

| 出口 | 触发 | 通知 |
|---|---|---|
| 帖子失效 | 服务端报告原因，或 `__T.locked != 0` | Toast「《标题》已失效，已停止跟踪（原因）」 |
| 长期无新回复 | 自最后回复起满 `keepDays` 天 | Toast「《标题》已多日无新回复，已停止跟踪」 |
| 用户主动移除 | 帖子菜单「停止跟踪」/ 跟踪 Tab 行内移除 / 全部移除 | 不提示（全部移除与行内移除各自有即时反馈） |

网络失败/解析失败**绝不停止跟踪**：只累计 `failCount` 并记录 `lastError`，下轮重试
（避免断网期间把跟踪列表清空）。

## 5. 已读语义

- 未读增量 = `totalReplies - seenReplies`；行上显示「+N 条新回复」，Tab 文案带未读任务数。
- **首次成功检查只建立基准**：新增跟踪后立刻做一次检查并把 `seenReplies` 设为当时回复数，
  刚添加的帖子不会立刻冒出红点（`lastCheckAt === 0` 判据）。
- 点开「跟踪」Tab 条目：本地立即置已读（红点马上消失）→ 打开帖子第 1 页（用户口径）。
- **手动打开被跟踪的帖子也算已读**：`ThreadPanel` 整页加载成功后调
  `appStore.markTrackedSeenOnOpen(tid)`，其内部**先检查、后置已读**——用户此刻看到的就是
  最新内容，若先按旧基准置已读、检查又发现新回复，会立刻出现「刚看过却又有红点」的假未读。
- **已读时点的服务端时间戳 `seenLastPostTs`**（第二个防假未读的闸门）：置已读时记下当时的
  「服务端最后回复时间」；检查成功时若 `本次最后回复 <= seenLastPostTs`，说明这批回复用户上次
  阅读时就已经存在，直接把基准推进到最新、不产生红点。这样即使点开帖子时的即时检查被 60 s
  最小间隔节流挡住（没重新查询），下一轮轮询也不会冒出「刚看过又有新回复」。
  刻意用服务端时间而不是设备时钟比较——设备时钟偏快会把晚到的新回复误判成「已看过」而吞掉提醒。
- 「全部已读」只推进基准，不改变跟踪关系。

## 6. 代码结构

| 文件 | 职责 |
|---|---|
| `model/TrackedThread.ets` | 跟踪任务模型、检查结果三态、停止通知、全部常量 |
| `common/utils/ThreadTrackPolicy.ets` | 纯函数：未读/超期/剩余天数判定、状态应用、排序、缓存校验、文案 |
| `parser/ThreadStatusParser.ets` | `__output=8` 响应解析（正常/失效/失败三态） |
| `service/api/ThreadTrackApi.ets` | `fetchThreadTrackStatus`（App 签名通道 + GB18030） |
| `store/TrackedThreadStore.ets` | 跟踪任务增删查、定时检查、已读、失效清理、持久化与红点发布 |
| `common/dialogs/ThreadTrackDialogs.ets` | 跟踪设置对话框内容（用途说明 / 时长选择 / 状态卡 / 停止跟踪） |
| `store/AppStore.ets` | 接轮询参与者、Facade 方法、停止通知 → Toast、退出登录 reset |
| `service/NgaClient.ets` | 新增 `postSignedPathGb`（GB18030 解码的签名 POST） |

UI 入口：

- **帖子页**（`ThreadPanel`）更多菜单新增「跟踪帖子更新」，已跟踪时文字变主色（`active`）；
  点击打开跟踪对话框——未跟踪显示用途 + 时长选择 + 「开始跟踪」，已跟踪额外显示状态卡
  （剩余天数 / 回复数 / 未读 / 上次检查）与内容区破坏色「停止跟踪」。
- **个人主页 →「收藏、保存与跟踪帖子」**（`FavoriteSavedPanel`）：第三 Tab「跟踪」列出跟踪
  任务，行内可移除；标题区右上角为「全部移除」（二次确认）。
- **消息中心**（`NotificationPanel`）：第四 Tab「跟踪」，未读排前并显示「+N 条新回复」，
  点击已读并打开帖子，右上角「全部已读」作用于跟踪系统；未读数并入标题栏铃铛角标
  （`TopicListPanel`）。

## 7. 测试

`entry/src/test/ThreadTrackUnit.test.ets`（已注册进 `List.test.ets`）覆盖 32 个用例：

- `threadTrackParser`（11 个）：正常响应（含 `subject`/`author`/`authorid`/`fid`/`locked`）、
  `__T` 字典形状、`replies` 缺失按 `__ROWS-1` 兜底、`replies` 为空串/非数字同样兜底、
  失效原因提取（只认 `data.__MESSAGE`）、**HTML 错误页与「有 data 但无业务错误体」一律按
  可重试失败**（防误删跟踪）、解析失败与空响应按「可重试」处理。
- `threadTrackPolicy`（21 个）：未读增量与零/负边界、未读计数、最后活动时间取
  「服务端时间与开始跟踪时刻的较晚者」、**新任务观察期内不被判超期**、按
  `lastpost` 与 `createdAt` 两条路径判超期、剩余天数、状态应用（成功 / 网络失败 / 失效 /
  锁定 / 超期 / 回复数减少 / 标题回填不产红点）、**已读时点之后的回复自动推进基准**及其反例、
  **作者与版块回填（已有作者不被覆盖）**、未读优先排序、缓存字段校验、停止文案、
  标题与副标题兜底。

## 8. 已知边界与后续可选项

- **通道风险**：`__output=8` 是网页版 output 值，虽实测在 App 签名通道可用，仍属「我们自己
  选的 output」。若将来失效，回退方案是改用 `__output=17` HTML + 从
  `commonui.postArg.setDefault(…, totalReplies, lastPostTs)` 轻量提取（`parser/nga/html-thread`
  已有该解析函数，只需从镜像入口导出）。
- **不做后台检查**（需要后台任务能力与通知权限）；应用不在前台时不检查，红点在下次前台
  轮询后补齐。
- **超期停止依赖检查成功**：网络持续失败时超期任务不会被移除（`failCount` 只做记录）。
  这是刻意取舍——「误停活跃帖」比「延迟停止」更糟，恢复联网后的下一次检查会立即补停。
- 跟踪 Tab 打开帖子固定第 1 页；若将来要「直达新回复所在页」，可用已读基准回复数换算页码。
- 跟踪未读**并入**标题栏铃铛角标（`TopicListPanel`），且跟踪 Tab 列出**全部**跟踪任务
  （有更新的排前、显示「+N 条新回复」）——这两条是实现时按推荐值定的，若你更想要
  「铃铛不并入」或「只列有更新的」，改动都很小。
